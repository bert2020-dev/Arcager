# Releasing and versioning

## The version number lives in one place

```python
# arcager.py
VERSION = "4.2.0"
```

That is the only place you ever edit. Everything else follows from it:

| What | How it follows |
|---|---|
| `arcager -V` / `--version`, `arcager --help` | read `VERSION` at run time |
| Titles such as "Arcager 4.2 architecture" in `README.md` and `docs/` | `python scripts/sync_docs.py` |
| The resource-type table and the full `--help` text in `docs/CLI.md` and the README | generated by the same command from the program itself |

### To release a new version

```bash
python scripts/sync_docs.py --set X.Y.Z     # edits VERSION, then updates every doc (X.Y.Z = your new version)
python scripts/run_tests.py                 # includes a check that the docs are in sync
# then add a section for the new version at the top of CHANGELOG.md (by hand)
```

(Or edit `VERSION` by hand and run `python scripts/sync_docs.py` with no arguments.)

`python scripts/sync_docs.py --check` changes nothing and exits `1` with instructions if any
document is stale. The test-suite runs it, so a forgotten sync fails CI instead of shipping.

### What is intentionally not changed automatically

* `docs/RELEASE_VALIDATION.md` is a dated record of one validation run. Update it by hand when
  you re-validate, otherwise it would claim a validation that never happened.
* `benchmarks/` uses labels such as `4.0.0` and `3.2.3` for fixed historical baselines.
* Sentences about when something was introduced ("in 4.0", "since 4.1") are history.
* The container format number (`<!--arcager:4-->`, `V4_VERSION`) is not the program version. It
  changes only when the file format changes incompatibly.

### If a heading is reworded

`scripts/sync_docs.py` finds each heading with a pattern (the `RULES` table). If you rewrite
one and the pattern no longer matches, the script and the test fail with the file name and the
pattern, and you update that one line of `RULES`.
